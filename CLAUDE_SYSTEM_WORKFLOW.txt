ANIMATION BITTRIX - END-TO-END SYSTEM WORKFLOW
===============================================

Purpose
-------
This file is a handoff document for Claude AI. It describes the workflow that
is implemented in this repository as of 2026-11-02. Treat the source code as
the final authority if this document and an older document disagree.

The product is a full-stack AI animation pipeline. A user submits a topic,
text, or URL. The active AI provider (Codex CLI) researches the content and
returns a validated narration plus scene plan. A human approves the plan,
Remotion renders a preview, a human approves the exact preview version, and
Remotion renders the final MP4 into the video library.

The canonical production contract is:

    submitted content
      -> Codex research and structured script/scene plan
      -> Gate 1: human script approval
      -> TTS, assets, captions, SFX, audio bed, and Remotion props
      -> headless Remotion preview render and automated QA
      -> Gate 2: approval of the exact current preview version
      -> final Remotion render using the exact approved preview inputs
      -> completed video in the library


1. SYSTEM COMPONENTS
---------------------

Frontend
  Location: frontend/
  Technology: React, Vite, TypeScript
  Development URL: http://localhost:5173
  Main UI areas: Dashboard, project detail, script review, preview review,
  final video library, settings, live progress/status.

Backend
  Location: backend/
  Technology: Node.js, Express, TypeScript, ESM
  Default URL: http://127.0.0.1:5000
  Responsibilities: REST API, PostgreSQL persistence, Codex process control,
  script versioning, approval enforcement, TTS, asset ingestion, render
  orchestration, media serving, and WebSocket progress events.

Database
  Technology: PostgreSQL
  Default database: animation_pipeline
  Default connection: postgres://postgres:postgres@127.0.0.1:5434/animation_pipeline
  Schema: database/schema.sql
  Main tables: projects, scripts, approvals, assets, jobs, render_jobs,
  videos, agent_runs.

AI provider
  Current provider: Codex CLI running on the same machine as the backend.
  Provider implementation: backend/src/modules/providers/codexProvider.ts
  Adapter contract: backend/src/modules/providers/providerAdapter.ts
  Claude is designed as a future/pluggable provider; it is not the active
  provider in the current runtime. Do not describe Claude as already running
  unless the provider implementation is changed and verified.

Animation engine
  Location: remotion/
  Technology: Remotion 4, React, Chromium/headless rendering
  Main composition: MainComposition
  Composition entry: remotion/src/Root.tsx
  Renderer: backend/src/modules/renders/videoRenderer.ts
  Render input: backend/media/render-data/<project>_<type>_v<version>.json

Audio and media
  TTS: local Kokoro model, with ffmpeg conversion and ffprobe duration checks.
  Captions: Whisper word timestamps when available, otherwise deterministic
  timing derived from the approved narration and measured audio duration.
  SFX: deterministic procedural SFX library generated by scripts/make_sfx.py.
  Bed: procedural audio bed generated by backend audio services.
  Assets: exact Codex-selected direct downloads, fetched by the backend after
  Gate 1 and stored by project and preview version.

Persistence and delivery
  Backend media is served at /media.
  Final videos are served from /media/videos/<project-id>_final.mp4.
  Preview videos are served from /media/previews/<project-id>_preview_v<N>.mp4.
  Generated media, audio, downloaded assets, and database data are not moved
  by git and should not be committed.


2. LOCAL STARTUP WORKFLOW
-------------------------

Required tools:
  - Node.js (repository documentation specifies 22.12+; package engines allow
    Node >=20.19.0)
  - npm and Git
  - Docker Desktop, or a compatible local PostgreSQL instance
  - ffmpeg and ffprobe
  - Python 3 and pip
  - Codex CLI, authenticated on the backend machine
  - A normal Chromium-capable host for Remotion rendering

Install dependencies from the repository root:

    npm run install:all

Create local environment files:

    cp backend/.env.example backend/.env
    cp frontend/.env.example frontend/.env

Start the system in separate terminals:

    npm run db:start
    npm run backend:dev
    npm run frontend:dev

Open http://localhost:5173.
Check the backend with http://127.0.0.1:5000/api/health.
Check Codex status from the Settings screen or the Codex auth endpoints.

Build/type verification:

    npm run build

This runs the backend build, frontend production build, and Remotion
TypeScript check. Remotion rendering may require a normal host environment
because restricted containers can block Chromium namespaces or localhost port
allocation.


3. END-TO-END REQUEST FLOW
---------------------------

Step 1 - User submits content

The user enters one of:
  - input_type=topic: a topic or idea
  - input_type=text: pasted article, notes, or transcript
  - input_type=url: a source URL

Frontend call:
  POST /api/projects
  Body: { input_content, input_type, title? }

Backend behavior:
  1. Derive a title if one was not supplied.
  2. Insert a project row with stage=research and status=Researching.
  3. Immediately call scriptsService.generateInitialScript(...).
  4. Return the completed project only after script v1 is stored.
  5. If script generation fails, keep the project for inspection but mark it
     stage=failed and status=Failed / Needs attention; the API returns an error.

Important implementation note:
  The database schema contains a jobs table, but the current project creation
  path does not enqueue and consume a durable research worker job. Initial
  research/script generation runs inline from the backend request flow.

Step 2 - Codex researches and creates script v1

File: backend/src/modules/scripts/scriptsService.ts

Codex receives the submitted content and input type. The provider loads the
repository video-production skill and the live Remotion renderer contract
before creating the plan. The renderer contract overrides generic skill
defaults when they conflict.

The Codex CLI is instructed to:
  1. Research the submitted topic when research is requested.
  2. Verify facts and provide source URLs and notes.
  3. Select candidate visual assets only when useful.
  4. Return exact direct-download URLs, source pages, license labels, and
     attribution for selected assets.
  5. Return only the required structured JSON; no TSX, downloaded files, or
     extra video deliverables.
  6. Create a supported blueprint scene plan with a hook first and CTA last.

The provider validates the returned plan before persistence. Required content
includes narration, scene data, colors, text, visual blueprint objects,
motion cues, continuity, asset metadata where relevant, and supported timing.
Invalid or incomplete plans are rejected before a render can start.

The stored scripts row contains:
  - project_id and monotonically increasing version
  - topic interpretation
  - research notes
  - sources
  - fact-check notes
  - complete narration
  - scene_plan JSON
  - change request notes for revised versions

The backend also stores an agent_runs audit row with provider, task, input and
output references, and token usage metadata. The project becomes:

    stage  = script_review
    status = Script ready for review

Step 3 - Gate 1: human reviews the script

The user reviews the narration, source information, and scene-by-scene plan in
the project detail screen. Gate 1 is explicit and version-specific.

Approve call:
  POST /api/projects/<project-id>/scripts/approve
  Body: { script_id, version_number, approved_by, feedback_notes? }

The backend checks that the selected script version exists and that the
script_id matches that version. It then records an approvals row with
approval_type=script and updates the project to:

    stage  = script_approved
    status = Script approved

No preview render may run until the requested script version has this approval.

If the user requests script changes:
  POST /api/projects/<project-id>/scripts/revise
  Body: { feedback, change_narration? }

The backend creates a new script version and preserves the old version. Unless
change_narration=true, the previously approved narration is passed through and
must remain unchanged; visual corrections alone do not rewrite narration.
Any existing preview approvals are deleted because a new plan invalidates the
old preview. The new version returns to script_review and must pass Gate 1
again.

Step 4 - Preview render request

Request call:
  POST /api/projects/<project-id>/previews/render
  Body: { script_version, visual_feedback? }

The backend first checks Gate 1 for that exact script version. It also refuses
to start if another preview for the project is queued or rendering.

On success it:
  1. Increments current_preview_version.
  2. Inserts a render_jobs row with render_type=preview and status=queued.
  3. Sets the project to preview_render / Rendering preview.
  4. Starts processing asynchronously and immediately returns the render job.

The browser listens to WebSocket /ws for render_progress events and refreshes
project data when rendering reaches 100 percent.

Step 5 - Prepare immutable preview inputs

File: backend/src/modules/renders/rendersService.ts
Method: writeRemotionSceneData(...)

For each approved scene the backend performs the following.

5a. Generate measured scene narration
  - Generate one Kokoro audio clip per scene.
  - Convert the model output to MP3 with ffmpeg.
  - Measure each clip with ffprobe.
  - Use the measured duration to drive scene frame allocation.
  - Preserve the approved words; never time-stretch the narration.
  - If the narration is too long, redistribute available scene frames and, if
    necessary, retry the same words at a supported faster Kokoro speed.
  - If the words still cannot fit the planned runtime, reject the render and
    ask for a shorter script/new Gate 1 approval.

5b. Validate scene data
  Each scene must have a supported blueprint visual type, blueprint object
  data, valid theme color, narration, subtitle, on-screen text, visual
  direction, motion cue, continuity, and duration between 2.5 and 5 seconds.

5c. Download exact Codex-selected assets
  - Inspect blueprint objects for image or downloaded 3D model specs.
  - Require a direct download URL supplied by Codex.
  - Download through assetFetcher; do not silently substitute another asset.
  - Record source URL, license, attribution, local path, media URL, size, and
    object/scene identity.
  - Inject project-local asset URLs into the Remotion props.
  - Authored vector/procedural visuals are used when no suitable licensed
    external asset is available.

5d. Build procedural sound cues
  - Seed the SFX library using project, render type, and preview version.
  - Resolve roles such as pop, click, tick, whoosh, slide, riser, impact,
    sparkle, chime, draw, count, and ding from object labels and motion.
  - Schedule cue hit frames to match visual entrances, purposeful movement,
    bullets, CTA, and transitions.
  - Shift the audio start frame by the measured transient so the audible hit
    lands on the intended visual frame.
  - Write a cue manifest beside the render props.

5e. Build continuous audio and captions
  - Generate one procedural background bed for the whole timeline.
  - Build word captions with Whisper timestamps when available.
  - Fall back to deterministic word timing based on measured scene audio.
  - Keep narration, SFX, bed, captions, and animation on the same 30 FPS clock.

5f. Write immutable render inputs
  Main props:
    backend/media/render-data/<project>_preview_v<preview>.json
  Cue manifest:
    backend/media/render-data/<project>_preview_v<preview>.json.cues.json
  Asset manifest:
    backend/media/projects/<project>/previews/v<preview>/asset-manifest.json
  Scoped SFX:
    remotion/public/projects/<project>/previews/v<preview>/audio/sfx/

The payload includes video metadata, scene list, frame durations, narration
URLs, background bed URL, captions, audio cues, style profile, and asset URLs.
It is marked generatedBy=codex and includes source project, script, and
preview versions. Remotion rejects stale/manual scene data without the proper
Codex provenance.

Step 6 - Headless Remotion preview render

The backend invokes:
  remotion/scripts/remotion-host.mjs render
  entry: src/index.ts
  composition: MainComposition
  props: the versioned preview JSON

Remotion reads the props through Root.tsx, registers MainComposition, and
renders BlueprintVisual/scene components using frame-driven motion. The
composition includes overlapping transitions, animated visuals, per-scene
narration, one continuous audio bed, deterministic SFX, and captions.

Current runtime format enforced by videoRenderer.ts:
  width  = 1080
  height = 1920
  fps    = 30

The renderer uses the configured render scale and Chromium concurrency/timeouts.
The generated file is:
  backend/media/previews/<project>_preview_v<preview>.mp4

Step 7 - Automated quality gates

The render is not considered successful until all checks pass:
  1. Remotion exits successfully.
  2. Output file exists and is not empty.
  3. ffprobe confirms 1080x1920 at 30 FPS.
  4. ffprobe confirms a usable audio stream.
  5. Scene stills and a contact sheet are rendered.
  6. scripts/qualityGate.mjs passes text overflow, zone overlap, and canvas
     bounds checks.
  7. The cue manifest exists.
  8. scripts/verify_sync.py passes audio/visual cue synchronization using
     NumPy and SciPy.

If any check fails, the render job becomes failed, the project becomes
failed / Failed / Needs attention, and no substitute video is published.

On success:
  render_jobs.status = completed
  render_jobs.progress = 100
  project stage/status = preview_review / Preview ready for review

Step 8 - Gate 2: human reviews the exact preview

The user watches the current preview version in the dashboard. The preview
approval must refer to the exact current preview version and a completed
preview render.

Approve call:
  POST /api/projects/<project-id>/previews/approve
  Body: { render_job_id, preview_version, approved_by, feedback_notes? }

The backend validates that the render job is a completed preview for that
project and version. It records approval_type=preview and updates the project:

    stage  = preview_approved
    status = Preview approved

If the user requests visual changes:
  POST /api/projects/<project-id>/previews/revise
  Body: { feedback }

This currently creates a new Codex script/scene-plan version while preserving
the narration. It deletes prior preview approvals, returns to script_review,
and requires Gate 1 before a new preview can be rendered.

Step 9 - Final render

Request call:
  POST /api/projects/<project-id>/final-render

The backend:
  1. Reads current_script_version and current_preview_version.
  2. Checks Gate 2 approval for the current preview version.
  3. Loads the exact approved preview props.
  4. Verifies the props script and preview versions still match the project.
  5. Copies preview props and the cue manifest to final render-data paths.
  6. Does not refetch assets, regenerate audio, or rebuild the scene plan.
  7. Runs the same Remotion render and quality checks.
  8. Writes backend/media/videos/<project>_final.mp4.
  9. Inserts a completed final render_jobs row.
  10. Inserts a videos row with approved preview/script versions, duration, and
      file size.
  11. Updates the project to completed / Completed.

The final video therefore uses the same content and media that the reviewer
approved in Gate 2.

5. PROJECT STATE MACHINE
------------------------

Normal path:

    draft
      -> research / Researching
      -> script_review / Script ready for review
      -> script_approved / Script approved
      -> preview_render / Rendering preview
      -> preview_review / Preview ready for review
      -> preview_approved / Preview approved
      -> final_render / Rendering final video [conceptual transition]
      -> completed / Completed

Revision loops:
  - Script feedback creates a new script version and returns to script_review.
  - Preview visual feedback also creates a new script/plan version and returns
    to script_review.
  - A new script version invalidates old preview approvals.
  - Gate approvals are version-specific; an old approval never transfers to a
    newer script or preview.

Failure path:
  Any failed initial script generation or failed preview/quality check marks
  the project failed / Failed / Needs attention and keeps diagnostic records
  for inspection.


6. DATABASE RECORD LIFECYCLE
----------------------------

projects
  One durable project row. Tracks input, current script version, current
  preview version, stage, status, and timestamps.

scripts
  Append-only version history for narration, research, sources, fact checks,
  and scene plans.

approvals
  Human decisions for script and preview gates, always tied to a version.

assets
  Asset metadata and provenance. The current render preparation also writes a
  JSON asset-manifest.json under the project preview directory.

jobs
  Generic queue schema for provider/job concepts. It exists for durable job
  expansion, but the currently traced create/render path uses direct service
  execution and render_jobs records.

render_jobs
  One record per preview/final render with type, versions, status, progress,
  output location, and errors.

videos
  Final library records, including the approved script and preview versions,
  duration, size, and storage URL.

agent_runs
  AI audit records and token usage metadata for Codex calls.

8. NON-NEGOTIABLE ENGINEERING RULES
------------------------------------

1. Never bypass Gate 1. No preview render without explicit approval of the
   exact script version.
2. Never bypass Gate 2. No final render without explicit approval of the
   exact current preview version.
3. Preserve approved narration during visual-only corrections.
4. Use the exact Codex-selected asset URLs and preserve source/license/
   attribution metadata. Do not silently substitute failed assets.
5. Keep picture and sound on one frame-driven clock at 30 FPS.
6. Keep scenes continuously animated with frame-driven motion, camera drift,
   and a persistent background. Do not use CSS animation, setTimeout, or
   wall-clock motion in Remotion scenes.
7. Use overlap transitions rather than fading through black unless explicitly
   requested by the plan.
8. Do not report a video as finished until the MP4 and all required validation
   results have been checked.
9. Keep secrets, provider tokens, .env files, generated media, downloaded
   assets, audio, and PostgreSQL data out of git.
10. Treat AI-generated data/code as untrusted. Validate it against the current
    renderer contract before storage or execution.


9. CURRENT IMPLEMENTATION NOTES FOR CLAUDE
-------------------------------------------

1. Codex is the active AI provider. The adapter interface includes future
   provider support, but no verified Claude runtime path should be assumed.
2. Project creation waits for initial script generation before returning.
3. Preview processing is asynchronous after the render job is inserted.
4. The current renderer enforces 1080x1920 at 30 FPS for rendered output,
   including the preview path. MOTION_PIPELINE.md contains an older rule that
   says previews should be 540x960; resolve this deliberately before changing
   the renderer or documentation.
5. The final render copies approved preview props and cue manifests. Do not
   refactor it to regenerate assets/audio unless the approval contract is also
   redesigned.
6. The live browser preview loads saved preview props through the backend and
   maps backend media URLs into Remotion-compatible public paths.
7. The jobs table is present in the schema, but the observed service path uses
   direct calls and render_jobs; do not claim a worker queue exists without
   tracing a new implementation.


10. SAFE CHANGE WORKFLOW FOR CLAUDE
-----------------------------------

Before changing code:
  1. Read this file plus the relevant source files listed above.
  2. Inspect git status and preserve unrelated user changes.
  3. Identify whether the change affects approval gates, versioning, media
     paths, render props, or audio synchronization.
  4. Update the smallest correct layer and keep the provider/renderer contract
     explicit.

After changing code:
  1. Run npm run build.
  2. For render changes, run the applicable scene-still, quality-gate, and
     audio-sync checks on a real render-data payload.
  3. Confirm no stale preview approval can authorize a newer version.
  4. Confirm generated files and secrets are not added to git.
  5. Report actual commands and results, including any checks that could not
     run because Chromium, Codex, PostgreSQL, Whisper, or Python dependencies
     were unavailable.

The intended Claude role is to understand this workflow first, then make
targeted, evidence-backed changes without weakening the two-gate approval
contract or the exact-preview finalization guarantee.
